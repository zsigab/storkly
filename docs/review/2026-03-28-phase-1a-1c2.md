## CRITICAL

### 1. `SEED_DATA` env var will never activate the DataSeeder

**Files:** `.env.example`, `backend/web/src/main/java/app/storkly/DataSeeder.java:28`

The DataSeeder uses `@ConditionalOnProperty(name = "storkly.seed-data")`.
Spring Boot's relaxed binding maps env var `STORKLY_SEED_DATA` to `storkly.seed-data`.
But ARCHITECTURE.md and `.env.example` both document `SEED_DATA=true` (no prefix).
Setting `SEED_DATA=true` does nothing — the seeder never activates.

**Fix:** Change `.env.example` and all documentation to use `STORKLY_SEED_DATA=true`,
or change the property name to `seed-data` (so `SEED_DATA` maps correctly).

**Spec:** ARCHITECTURE.md section 9, section 12 Phase 1M.

### 2. `StorklyApplicationTests` is a no-op

**File:** `backend/web/src/test/java/app/storkly/StorklyApplicationTests.java`

The test lacks `@SpringBootTest` — it is a plain JUnit class with an empty body.
It will always pass regardless of whether the Spring context loads.

**Fix:** Either add `@SpringBootTest` + Testcontainers wiring (per AGENTS.md),
or delete it. A green test that tests nothing is worse than no test.

**Spec:** AGENTS.md Integration Test Pattern section.

---

### 3. JWT stored in localStorage instead of httpOnly cookies

**File:** `frontend/src/api/client.ts:6-18`

The client stores tokens in `localStorage` and injects them as `Authorization: Bearer`.
AGENTS.md Auth section specifies: "JWT: access token 15 min, refresh token 7 days,
stored in httpOnly cookies."

localStorage-based tokens are vulnerable to XSS. This must be redesigned in Phase 1D
when auth is implemented. The current scaffolding sets the wrong pattern.

**Fix:** Remove `saveTokens`/`clearTokens`/`getAccessToken` from `client.ts`.
Auth token handling should be cookie-based and designed in Phase 1D.

**Spec:** Backend AGENTS.md Auth section.

## MAJOR

### 4. JOOQ version mismatch: plugin 3.20.3 vs library 3.21.1

**Files:** `backend/settings.gradle.kts:12`, `backend/gradle/libs.versions.toml:4`

`settings.gradle.kts` hardcodes the JOOQ plugin version as `3.20.3`.
`libs.versions.toml` declares `jooq = "3.21.1"`.
The codegen plugin and runtime library are different versions — this can cause
subtle incompatibilities in generated code.

Additionally, all plugin versions in `settings.gradle.kts` are hardcoded strings
instead of referencing the version catalog. Same for the root `build.gradle.kts`
(Spotless plugin ID hardcoded).

**Fix:** Sync `settings.gradle.kts` plugin versions with the catalog.
AGENTS.md says: "Never hardcode versions — always reference the catalog."

**Spec:** Backend AGENTS.md "Gradle Version Catalog" section.

---

### 5. `scraper` module included in Phase 1 build

**Files:** `backend/settings.gradle.kts:24`, `backend/web/build.gradle.kts:14`

The `scraper` module is listed in `settings.gradle.kts` and `web` depends on it
(`implementation(project(":scraper"))`). It's an empty shell, but it's compiled
and included in the fat JAR.

**Fix:** Remove `scraper` from `settings.gradle.kts` and `web/build.gradle.kts`
until Phase 2C. Re-add it when scraping work begins.

**Spec:** Backend AGENTS.md "Do NOT add features not in the current phase."

### 6. Default active profile hardcoded to `local`

**File:** `backend/web/src/main/resources/application.yml:5`

`spring.profiles.active: local` means forgetting to set `SPRING_PROFILES_ACTIVE`
in production silently falls back to local settings (localhost DB, test CAPTCHA key).
Combined with the `docker-compose.yml` relying entirely on `.env` for the profile,
this is a deployment risk.

**Fix:** Remove the default from `application.yml`. Require the profile to be
set explicitly. Add `SPRING_PROFILES_ACTIVE: prod` directly to the base
`docker-compose.yml` api service environment.

### 7. Frontend is the unmodified Vite starter template

**Files:** `frontend/src/App.tsx`, `frontend/src/main.tsx`, `frontend/src/App.css`,
`frontend/src/index.css`

The frontend has the default Vite React template: counter demo, purple accent colours,
`default export` on App, non-null assertion `!` in main.tsx, CSS files instead of
Tailwind.

None of the Phase 1I dependencies are installed: no Tailwind CSS v4, no Shadcn/UI,
no React Router, no TanStack Query, no Zod, no React Hook Form.

**Note:** This is expected since Phase 1I hasn't started yet. However, the template
files actively violate AGENTS.md rules (default export, non-null assertion, hardcoded
colours). These should be cleaned up when 1I begins — flag for tracking.

**Spec:** Frontend AGENTS.md "CRITICAL — Do NOT" rules 2, 3; ARCHITECTURE.md section 5.

### 8. Missing strict TypeScript options

**File:** `frontend/tsconfig.app.json`

`noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` are not set.
AGENTS.md requires both.

**Fix:** Add to `compilerOptions`:
```json
"noUncheckedIndexedAccess": true,
"exactOptionalPropertyTypes": true
```

Also add `"baseUrl": ".", "paths": { "@/*": ["./src/*"] }` for the Shadcn `@/`
import convention.

**Spec:** Frontend AGENTS.md "Strict mode" section.

## MINOR

**File:** `backend/Dockerfile:8-9`

Line 8 `COPY ... gradle/ ./` copies gradle/ contents into workspace root.

### 11. Dockerfile uses JDK for runtime stage

**File:** `backend/Dockerfile:19`

Uses `eclipse-temurin:26-jdk` for runtime. Should be `eclipse-temurin:26-jre`
for a smaller image and reduced attack surface. Acceptable if JRE image is not
yet available for Java 26 EA.

### 12. `docker-compose.override.yml` missing seed data env var

**File:** `docker-compose.override.yml`

No `STORKLY_SEED_DATA: "true"` in the api service environment. Local Docker Compose
runs won't seed data for UI development.

### 13. `/swagger-ui/*` not proxied in Caddyfile

**Files:** `Caddyfile`, `Caddyfile.local`

`handle /api/*` proxies API calls, but `/swagger-ui.html` is outside `/api/`.
It will be served by the static file server (404 or index.html fallback).

**Fix:** Either move swagger-ui under `/api/swagger-ui` in springdoc config,
or add `handle /swagger-ui/*` to Caddyfile.

---

### 14. `spring-boot-starter-test` in `util` module

**File:** `backend/util/build.gradle.kts:8`

The util module is documented as "pure Java, zero Spring dependencies."
Having `spring-boot-starter-test` in test scope technically doesn't violate
the runtime constraint, but is unnecessarily heavy. JUnit 5 alone would suffice.
