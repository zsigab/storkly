# Phase 1D Review — Auth (Email/Password)

**Date:** 2026-03-28
**Scope:** Phase 1D auth implementation: registration, login, email verification, password reset, JWT cookies, CAPTCHA

---

### 1. Jackson 2 import in TurnstileResponse

**Severity:** CRITICAL

**Files:** `backend/service/src/main/java/app/storkly/service/auth/TurnstileResponse.java:3`

Uses `com.fasterxml.jackson.annotation.JsonProperty` (Jackson 2). AGENTS.md explicitly forbids Jackson 2 imports — Spring Boot 4 ships Jackson 3 with `tools.jackson.*` packages.

This will **fail at runtime** if Spring Boot 4 only bundles Jackson 3 on the classpath. Even if Jackson 2 is transitively present now, it may deserialize through the wrong `ObjectMapper`.

**Fix:** Change the import to `tools.jackson.annotation.JsonProperty`. Verify the annotation exists in Jackson 3; if the `@JsonProperty` API is different, use `@tools.jackson.annotation.JsonProperty("error-codes")`.

**Spec:** `backend/AGENTS.md` section "CRITICAL -- Do NOT", bullet on Jackson 2 imports.

### 2. JOOQ version mismatch between settings.gradle.kts and libs.versions.toml

**Severity:** CRITICAL

**Files:** `backend/settings.gradle.kts:11`, `backend/gradle/libs.versions.toml:4`

`settings.gradle.kts` hardcodes the JOOQ codegen plugin version as `3.20.3`, but `libs.versions.toml` declares `jooq = "3.21.1"`. The codegen plugin version must match the library version exactly, otherwise the generated code may be incompatible with the runtime JOOQ library.

**Fix:** Remove the hardcoded version from `settings.gradle.kts` and use the version catalog reference. The plugin is already declared in `[plugins]` section of the toml as `jooqCodegen` with `version.ref = "jooq"`. In `settings.gradle.kts`, change:
```kotlin
id("org.jooq.jooq-codegen-gradle") version "3.20.3"
```
to either reference the catalog or update to `3.21.1`.

**Spec:** `backend/AGENTS.md` section "Gradle Version Catalog" ("Never hardcode versions"), `docs/REVIEWER.md` "JOOQ codegen version matches library version".

### 3. Frontend index.ts exports non-existent saveTokens/clearTokens

**Severity:** CRITICAL

**Files:** `frontend/src/api/index.ts:1`

The barrel export `export { api, saveTokens, clearTokens } from "./client"` references `saveTokens` and `clearTokens` which do not exist in `client.ts`. ADR-009 explicitly states these helpers were removed when switching to httpOnly cookies. This will cause a **TypeScript compilation error**.

**Fix:** Change to:
```ts
export { api } from "./client";
```

**Spec:** `docs/decisions/009-jwt-httponly-cookies.md` ("The `saveTokens`/`clearTokens`/`getAccessToken` helpers in `client.ts` are removed").

### 4. Integration tests use WebTestClient instead of RestTestClient

**Severity:** MAJOR

**Files:** `backend/web/src/test/java/app/storkly/auth/AuthControllerIntegrationTest.java:14,33`

Uses `org.springframework.test.web.reactive.server.WebTestClient`. AGENTS.md mandates `RestTestClient` for Spring Boot 4 integration tests. `WebTestClient` also requires `spring-boot-starter-webflux` on the test classpath, which is not declared in `web/build.gradle.kts` -- the tests may fail to compile or run.

**Fix:** Replace `WebTestClient` with `RestTestClient` (from `org.springframework.boot.test.web.client`). Update all chained assertions to match `RestTestClient` API.

**Spec:** `backend/AGENTS.md` section "CRITICAL -- Do NOT" ("Do NOT use `TestRestTemplate` in new tests. Use `RestTestClient`"), section "RestTestClient for Integration Tests".

### 5. Brace style violations: catch/else on same line as closing brace

**Severity:** MAJOR

**Files:**
- `backend/web/src/main/java/app/storkly/auth/JwtService.java:39` (`} catch`)
- `backend/service/src/main/java/app/storkly/service/email/EmailService.java:44` (`} catch`)
- `backend/web/src/main/java/app/storkly/infrastructure/UserRepositoryImpl.java:48` (`} else {`)

AGENTS.md requires `catch`, `else`, `else if`, and `finally` to start on a **new line**. All three files have them on the same line as the closing brace.

**Fix:** Move `catch`/`else` to new lines:
```java
}
catch (JwtException | IllegalArgumentException e) {
```
```java
}
else {
```

Note: Spotless with Palantir Java Format may handle this automatically. Run `./gradlew spotlessApply` and verify it produces the correct style.

**Spec:** `backend/AGENTS.md` section "Braces".

### 6. Hardcoded email URLs in EmailService

**Severity:** MAJOR

**Files:** `backend/service/src/main/java/app/storkly/service/email/EmailService.java:22,30`

Both `sendEmailVerification` and `sendPasswordReset` hardcode `http://localhost:5173` as the frontend URL. This will break in production where the frontend runs at `https://storkly.app`.

**Fix:** Add a `baseUrl` (or `frontendUrl`) property to `EmailProperties` (or a new config property) and inject it. Each profile (`application-local.yml`, `application-prod.yml`) sets the correct value.

**Spec:** `backend/AGENTS.md` section "CRITICAL -- Do NOT" ("Do NOT hardcode secrets"), `docs/ARCHITECTURE.md` section 9 (profiles table).

### 8. Cookies not marked Secure

**Severity:** MAJOR

**Files:** `backend/web/src/main/java/app/storkly/auth/AuthController.java:89-105`

The `setAccessTokenCookie` and `setRefreshTokenCookie` methods do not call `cookie.setSecure(true)`. Without the `Secure` flag, cookies will be sent over plain HTTP, making them vulnerable to interception. In production (HTTPS via Caddy), this is a real risk if the flag is missing.

For local development over HTTP, the Secure flag would prevent cookies from being sent. Consider making this configurable per profile, or always setting it and using HTTPS locally via Caddy.

**Fix:** Add `cookie.setSecure(true)` to both cookie-setting methods. If local dev needs HTTP, make the secure flag profile-dependent via a property.

**Spec:** `docs/decisions/009-jwt-httponly-cookies.md` (security best practice for httpOnly cookies), `docs/REVIEWER.md` security section.

### 9. User.isEnabled() blocks login for unverified users but AuthService.authenticate() does not check

**Severity:** MAJOR

**Files:**
- `backend/domain/src/main/java/app/storkly/domain/user/User.java:57-59`
- `backend/service/src/main/java/app/storkly/service/auth/AuthService.java:61-67`

`User.isEnabled()` returns `false` when `emailVerifiedAt` is null, but `AuthService.authenticate()` only checks password matches -- it does not check `isEnabled()`. The login endpoint returns a valid JWT for unverified users. The `isEnabled()` method is only effective if Spring Security's `UserDetailsService` authentication flow is used, which it is **not** (the controller calls `authService.authenticate()` directly).

The integration test `login_validCredentials_setCookies` expects a 401 for an unverified user, which suggests the intended behavior is to block unverified logins. But the 401 in the test likely comes from `UserNotFoundException` being thrown (since the user is not found by email after registration without verification) -- actually looking more carefully, the user IS found but `authenticate()` would return the user successfully if password matches, then JWT is issued. The test comment says "returns 401" which may only pass because of a side effect.

**Fix:** Add an `isEnabled()` check in `AuthService.authenticate()`:
```java
if (!user.isEnabled()) {
    throw new AccessDeniedException("Email not verified");
}
```

**Spec:** `docs/ARCHITECTURE.md` F-07 ("email verification required"), `backend/AGENTS.md` security section.

### 10. No @ConfigurationPropertiesScan reach into service module

**Severity:** MINOR

**Files:** `backend/web/src/main/java/app/storkly/StorklyApplication.java:8-9`

`@ConfigurationPropertiesScan` scans from the `app.storkly` package, which covers the `web` module. The `service` module's `@ConfigurationProperties` records (`TurnstileProperties`, `JwtProperties`, `EmailProperties`) are in `app.storkly.service.*`. This works because `@ConfigurationPropertiesScan` scans the package and sub-packages of the annotated class. This is fine as-is -- noting for clarity.

**Fix:** None needed.

### 12. DataSeeder users have no emailVerifiedAt set

**Severity:** MINOR

**Files:** `backend/web/src/main/java/app/storkly/DataSeeder.java:58-76`

Seed users do not set `email_verified_at`, so they are "unverified." Since `User.isEnabled()` returns `false` for unverified users, seeded users cannot log in (once the isEnabled check from finding #9 is added). This makes the DataSeeder less useful for UI development.

**Fix:** Add `.set(USER.EMAIL_VERIFIED_AT, OffsetDateTime.now())` to both seed user inserts.

**Spec:** `docs/ARCHITECTURE.md` section 9 (DataSeeder should insert usable test data).

### 13. JwtService recreates SecretKey on every call

**Severity:** MINOR

**Files:** `backend/web/src/main/java/app/storkly/auth/JwtService.java:63-65`

`signingKey()` creates a new `SecretKey` from the secret string on every invocation (generate, validate, extract). This is a minor performance concern -- the key should be computed once and cached.

**Fix:** Compute the `SecretKey` once in a `@PostConstruct` method or lazy field and reuse it. This is a good candidate for `StableValue` (Java 26 feature mentioned in AGENTS.md).

**Spec:** `backend/AGENTS.md` section "Lazy Constants (StableValue)".

### 14. AuthService.authenticate() throws misleading InvalidTokenException

**Severity:** MINOR

**Files:** `backend/service/src/main/java/app/storkly/service/auth/AuthService.java:66`

Wrong password throws `InvalidTokenException("Invalid credentials")`. This exception type is semantically wrong -- it is an authentication failure, not an invalid token. The `GlobalExceptionHandler` maps `InvalidTokenException` to 401, so the HTTP status is correct, but the exception name is misleading.

**Fix:** Create an `InvalidCredentialsException` (extending `DomainException`) or use a more generic `AuthenticationFailedException`. Map it to 401 in `GlobalExceptionHandler`.

**Spec:** `backend/AGENTS.md` section "Error Handling & HTTP Codes" (typed domain exceptions).

The catalog includes `jacksonDatabind = { module = "com.fasterxml.jackson.core:jackson-databind" }` which is a Jackson 2 artifact. While it is not used in any `build.gradle.kts`, its presence is confusing and risks accidental use.

### 16. EmailVerificationRepository.consume() updates User table directly

**Severity:** MINOR

**Files:** `backend/web/src/main/java/app/storkly/infrastructure/EmailVerificationRepositoryImpl.java:48-52`

The `consume()` method in `EmailVerificationRepositoryImpl` updates the `user.email_verified_at` column directly. This mixes concerns -- a repository for email verification tokens should not also update the `User` table. The `AuthService.verifyEmail()` method just delegates to `consume()` and does nothing else with the result.

**Fix:** Have `consume()` return the `userId` (like `PasswordResetRepository.consume()` does), then have `AuthService.verifyEmail()` call `userRepository` to set `emailVerifiedAt`. This keeps repository responsibilities clean.

**Spec:** `backend/AGENTS.md` ("Services orchestrate, Helpers map").
