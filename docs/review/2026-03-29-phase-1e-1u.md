## New Findings

### 1. HIDDEN visibility not enforced in ItemService, ClaimService, CategoryService

**Severity:** CRITICAL

**Files:**
- `backend/service/src/main/java/app/storkly/service/item/ItemService.java:148-160`
- `backend/service/src/main/java/app/storkly/service/item/ClaimService.java:110-122`
- `backend/service/src/main/java/app/storkly/service/category/CategoryService.java:27-31`

`assertReadAccess()` in `ItemService` and `ClaimService` only checks for `PRIVATE` visibility. `HIDDEN` registries are completely unprotected in these services — any authenticated user (or anonymous user for items/claims on non-private registries) can:
- List all items in a HIDDEN registry via `GET /api/registries/{slug}/items`
- View individual items via `GET /api/items/{id}`
- Claim items in a HIDDEN registry via `POST /api/items/{id}/claims`
- List claims on items via `GET /api/items/{id}/claims`
- List categories via `GET /api/registries/{slug}/categories`

`RegistryService.findBySlug()` correctly enforces HIDDEN (line 53-56), but the other services have their own `assertReadAccess()` copies that lack the HIDDEN check.

`CategoryService.findByRegistry()` has an additional issue: it only checks `visibility == PRIVATE && currentUserId == null`. An authenticated user who is NOT a subscriber can read categories of any PRIVATE registry.

**Fix:** Extract a shared access-control method (or have each service delegate to `RegistryService.findBySlug()` which already has correct logic) and apply to all services. The check should be:

```java
if (registry.visibility() == RegistryVisibility.HIDDEN) {
    if (currentUserId == null
        || (!registry.ownerId().equals(currentUserId)
            && !coOwnerRepository.isCoOwner(registry.id(), currentUserId))) {
        throw new AccessDeniedException("Registry is hidden");
    }
}
if (registry.visibility() == RegistryVisibility.PRIVATE) {
    if (currentUserId == null) {
        throw new AccessDeniedException("Registry is private");
    }
    boolean hasAccess = registry.ownerId().equals(currentUserId)
        || coOwnerRepository.isCoOwner(registry.id(), currentUserId)
        || subscriptionRepository.exists(currentUserId, registry.id());
    if (!hasAccess) {
        throw new AccessDeniedException("Registry is private");
    }
}
```

**Spec:** ARCHITECTURE.md 1T ("HIDDEN: owner + co-owners only"), F-08.

### 2. HIDDEN visibility excludes co-owners

**Severity:** MAJOR

**File:** `backend/service/src/main/java/app/storkly/service/registry/RegistryService.java:53-56`

The one place that *does* check HIDDEN only allows the owner:
```java
if (registry.visibility() == RegistryVisibility.HIDDEN) {
    if (currentUserId == null || !registry.ownerId().equals(currentUserId)) {
        throw new AccessDeniedException("Registry is hidden");
    }
}
```

Per ARCHITECTURE.md 1T, HIDDEN should allow "owner + co-owners only". Co-owners are locked out.

**Fix:** Add co-owner check: `!registry.ownerId().equals(currentUserId) && !coOwnerRepository.isCoOwner(registry.id(), currentUserId)`

**Spec:** ARCHITECTURE.md 1T, F-12.

### 3. Unsubscribe does not check for active claims (backend)

**Severity:** MAJOR

**File:** `backend/service/src/main/java/app/storkly/service/registry/RegistryService.java:143-147`

`unsubscribe()` unconditionally deletes the subscription. The frontend disables the button when `userHasClaims` is true (RegistryPage.tsx:186), but the backend does not enforce this. A direct API call bypasses the frontend guard.

```java
public void unsubscribe(String slug, UUID currentUserId) {
    Registry registry = registryRepository.findBySlug(slug)...;
    subscriptionRepository.delete(currentUserId, registry.id());
}
```

**Fix:** Before deleting, check if the user has active (unreleased) claims on any item in the registry. If so, throw a `ConflictException` (409). Defense in depth — never rely solely on frontend validation.

**Spec:** Commit message 97dc1b7 ("block when has claims").

### 6. CategoryService.findByRegistry() allows any authenticated user to read PRIVATE registry categories

**Severity:** MAJOR

**File:** `backend/service/src/main/java/app/storkly/service/category/CategoryService.java:27-32`

```java
public List<Category> findByRegistry(String slug, @Nullable UUID currentUserId) {
    Registry registry = ...;
    if (registry.visibility() == RegistryVisibility.PRIVATE && currentUserId == null) {
        throw new AccessDeniedException("Registry is private");
```

**Fix:** Apply the same access control as `ItemService.assertReadAccess()` (with the HIDDEN fix from #1).

### 7. Duplicate assertReadAccess logic across 3 services

**Severity:** MINOR (code smell, root cause of #1 and #6)

**Files:**
- `backend/service/src/main/java/app/storkly/service/item/ItemService.java:148-160`
- `backend/service/src/main/java/app/storkly/service/item/ClaimService.java:110-122`

- `backend/service/src/main/java/app/storkly/service/registry/RegistryService.java:50-68`

Four different implementations of registry access control with inconsistent logic. This is why the HIDDEN bug exists — the logic was added to `RegistryService` but not propagated to the copies.

**Fix:** Extract a `RegistryAccessService` (or add a public `assertReadAccess(Registry, UUID)` to `RegistryService`) and call it from all services. Single source of truth for access control.

### 9. No global 401 interceptor in frontend

**Severity:** MINOR

**File:** `frontend/src/api/client.ts`

If a JWT expires mid-session, API calls return 401 but there's no automatic logout or redirect to login. The user sees broken state until they manually navigate. This is not a bug per se (the backend refresh token flow handles most cases), but worth noting as a UX gap.

**Fix:** Add a response interceptor in the API client or a TanStack Query `onError` handler that clears auth state and redirects to `/login` on 401.

### 10. Category sort order reorder is not atomic

**Severity:** LOW

**File:** `backend/web/src/main/java/app/storkly/infrastructure/CategoryRepositoryImpl.java:72-78`

`updateSortOrders()` issues N separate UPDATE statements in a loop. While this runs within a `@Transactional` boundary (from `CategoryService.reorder()`), a mid-transaction failure would roll back, so data integrity is preserved. However, N round-trips is inefficient for large category lists.

**Fix:** Consider using a JOOQ batch update. Not urgent — category lists are small (typically < 20).

## Verdict

**🚫 Needs work**

The HIDDEN visibility bypass (#1) is a clear authorization bug — any user can access items, claims, and categories in HIDDEN registries. This, combined with the missing co-owner check (#2), the unvalidated unsubscribe (#3), and the PRIVATE category leak (#6), means the access control layer has real gaps. The root cause is duplicated access-control logic (#7) that drifted when HIDDEN was added.

Backend test coverage (#4) is also a blocker — the architecture mandates tests from 1D onward, and 7+ phases have shipped without any backend tests beyond the original 1D set.

**Recommended fix order:**
1. Extract shared `assertReadAccess` logic and fix HIDDEN + PRIVATE checks (#1, #2, #6, #7)
2. Add backend claim check to unsubscribe (#3)
3. Add backend tests for access control, then remaining features (#4, #5)
4. Address minor items (#8, #9, #10)
